# 3 方法：状态感知 Agent 调度管线

## 3.1 总体架构

本文提出的状态感知 Agent 调度管线，以"底层时空表征 + 独立上层规划调度层"为总体架构。底层统一采用 Marble（World Labs 公司）动态高斯生成模型作为时空表征基底；上层为状态感知 LLM-Agent 驱动的规划调度层，负责全局状态理解、任务拆解、逻辑规划与管线调度。

为保持表述清晰，本文在方法描述中直接使用相关软件与模型的名称及版本号；文中出现的商业产品与软件名称仅用于技术标识与可复现性说明，不构成对其的推荐、比较或商业背书。

管线运行遵循"感知—规划—调度—执行—更新"的五阶段闭环，其数据流如图 1 所示。

该架构与既有工作的区别在于：底层生成能力完全沿用统一的公开模型，不作任何模型训练、微调或算法改造；全部创新收敛于上层的规划调度逻辑与状态接地机制。这一约束保证了实验中下层生成能力的一致性，使架构增益可被干净地归因。

## 3.2 状态接地层

### 3.2.1 设计动因

智能体范式要求依托真实、结构化的环境状态进行推理[5]。然而，本文对 Marble 公开 API 的实际调用显示，其单次世界生成的导出物包括：高斯泼溅文件（SPZ/PLY）、碰撞网格（GLB）、360 全景图（PNG），以及一段由模型自动生成的自然语言场景描述（caption）；其语义元数据仅为尺度因子与地面偏移两个标量。

换言之，底层世界模型输出的是非结构化的几何与文本，既无物体列表，也无空间位置、关联关系与物理参数的显式表达。若直接将这些原始输出交给语言模型，智能体缺乏可用于全局推理的结构化状态，容易产生幻觉或调度错误。这一缺口正是状态接地层的设计动因。

需要说明的是，“将非结构化环境解析为可推理的结构化状态”本身并非新问题，机器人与具身智能领域对此已有成熟积累，如 3D 场景图[17]、ConceptGraphs[18] 与以场景图为中介的语言模型规划 SayPlan[19]（见 2.2 节）。本文的状态接地层在机制上与这些工作同源，其差异不在“是否使用结构化状态”，而在于所服务的对象：机器人场景图面向可导航、可操作的任务，本文的状态快照则面向可渲染、可编辑、可交互的生产语境——场景是被生成的对象，其全局状态需要从生成物中反推并持续维护，而非在既存环境中直接获取。

### 3.2.2 数据来源

状态接地层的输入、融合与输出关系如图 2 所示。状态接地层从三类异构输入中构建结构化状态：

（1）语义文本流：Marble 返回的 caption 自然语言描述。实测表明该描述质量较高，包含场景中的物体类型、材质与空间关系，可直接为语言模型提供语义先验。

（2）几何流：Marble 导出的碰撞网格（GLB）与高斯泼溅点云。实测显示，该网格不仅不含物体级语义标签，且被烘焙为一整块合并几何——连通域分割只能得到极少量的几何块，无法据此恢复物体级包围盒。因此几何流的作用被界定为提供**空间占用与整体尺度**（如体素占用分析），用于描述场景的空间结构与校验语义推理结果，而非单独承担物体切分。

（3）视觉流：360 全景图（正式模型提供）。由于几何流无法单独恢复物体级语义，全景图经多模态语言模型进行视觉理解，成为反推物体布局与语义类别的主要来源。

图 2　状态接地层的输入流、融合策略与结构化状态输出

### 3.2.3 状态快照结构

状态接地层将上述输入解析、融合为结构化的全局状态快照：其中物体级语义主要来自自然语言描述与全景图的视觉理解，空间占位与尺度来自几何流的占用分析，二者相互校验，其核心字段如下（示意）：

```
{
  "scene": "<场景语义标签>",
  "objects": [
    {"id": "...", "type": "<物体类别>", "bbox": [...],
     "position": [...], "physics": {"collision": ..., "material": ...}}
  ],
  "relations": [{"subject": "...", "object": "...", "relation": "<空间关系>"}],
  "hierarchy": {...},
  "physics_missing": ["<缺失物理参数的物体>"]
}
```

该快照是智能体进行环境状态接地感知的结构化输入来源，并在每轮调度后由 UE5 场景图回读更新，形成状态的持续维护。需要强调的是，状态接地层是本研究面向生产语境设计并实现的产物，而非底层模型的原生能力；其机制与机器人领域的场景接地规划同源，本文的贡献在于将该机制适配到“从生成物反推并维护全局状态”的场景生产任务，并检验其对调度表现的贡献。为便于与既有工业标准衔接，状态快照可序列化为通用场景描述格式（如 OpenUSD/glTF）作为交换载体，本文的创新则聚焦于语义解析与接地过程本身，而非自定义数据结构。

## 3.3 状态感知 LLM-Agent

状态感知 LLM-Agent 是上层规划调度模块的工程实现。它依托语言模型的原生推理能力，以上一阶段生成的结构化状态快照为感知输入，完成三项核心工作：

（1）全局状态理解：依据状态快照，识别当前场景的物体构成、空间布局与物理约束，形成对整体场景的认知。

（2）逻辑推理与任务拆解：依据高层创意意图与当前状态的差异，将"目标场景"分解为有序的子任务（如"生成某类资产""调整某物体位置""补充某物体的碰撞参数"）。

（3）层级规划与调度决策：将子任务组织为分层的执行序列，并生成相应的调度指令，交由下游网关执行。

本文的实现采用同一多模态大语言模型（deepseek-flash，DeepSeek-V4.1-Flash；DeepSeek 公司）作为推理载体，推理过程不作任何模型训练或微调。

## 3.4 MCP 协议网关与执行闭环

调度指令通过 MCP（Model Context Protocol）协议网关下发至执行层。网关承担两类调度：一是调用 Marble（marble-1.1）的生成接口产出场景资产；二是驱动 UE5（Unreal Engine 5，Epic Games 公司）引擎完成场景编辑、物体排布与物理参数配置。执行完成后，UE5 场景图被回读并交由状态接地层解析，更新全局状态快照，从而闭合"感知—规划—调度—执行—更新"的循环。

需要说明的是，执行层涉及的关键依赖在部署上分为两层：其一为三维高斯资产的引擎内渲染导入，需借助第三方插件在 UE5 中呈现；其二为智能体对引擎的操作控制，通过 MCP 协议实现。二者相互独立，本文方法聚焦于后者所代表的调度逻辑。

需要明确本文的验证范围：上述闭环描述的是管线架构及其数据流；本文实验实际完成验证的是其中的状态接地层与智能体调度两个环节（第 4 章），调度方案的质量以场景任务书为准进行程序化测量。至于 MCP 网关对引擎的实际驱动与引擎场景图的回读更新，属架构设计层面，其端到端执行依赖第三方渲染插件，本文未开展端到端验证，相应结论亦不以此为依据。

## 3.5 与低层表征的关系界定

本文方法中的规划调度属于叠加于 4D 高斯时空表征之上的上层功能模块，并不改变底层时空表征的维度定义。全文始终区分两个层次：底层为由 Marble 输出的四维动态高斯场景，上层为由智能体实现、并受状态接地层支撑的规划调度功能层。这一界定避免了与既有"第五维"宣传叙事的混淆，也使本文的创新边界保持清晰。
